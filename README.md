# 中文问答 · FastAPI 官方文档助手（RAG）

> **中文提问 → 查英文官方文档 → 用中文回答，并标注答案出自哪个文件。**
>
> 语料：FastAPI 官方文档 **154 篇 Markdown / 0.75 MB**，切成 **1919 个文本块**。
> 检索：向量（bge-m3）+ BM25 混合，含相关性阈值与联动闸门。
> 生成：火山方舟（OpenAI 兼容接口），embedding 全程本地。
>
> ⚠️ **建库时排除了 `release-notes.md`（更新日志）**：它按 PR 逐条罗列，每个主题都提一句但不说全，
> 一个文件就占 **2010 块 / 51.2%**，BM25 上轻松拿 13~20 分。排除后块数 3929 → 1919。
> 但 **L1 没变（旧 24 题集口径仍 21/29）** —— 它不是瓶颈。真正把 L1 往前推的是另外两步，见「关键决策 6」。

---

## 这个项目在解决什么

中文开发者读英文文档有两个痛点：**语言门槛**（想搜得先知道英文关键词）和**没法追溯出处**。

**先验证过一件事**：直接问大模型，对 FastAPI 这种热门框架它答得挺好——
裸问了 7 个细节问题（冷门、有版本坑），**7 题全对**，还主动标注了"这里我不确定"。
因为它是热门框架，训练数据里全是。

所以这个项目的价值**不在"答得更准"**，而在两件事：

1. **能给出处** —— 答案里的 `[1][2]` 能对回到具体文件
2. **能换成模型不知道的资料** —— 换语料即换领域（公司内部 API、项目规范）

> **RAG 的本质是「用可核实换知识广度」。**
> 在私有资料上这个交换是赚的；在模型已滚瓜烂熟的热门框架上，**是亏的**——这个项目诚实地记录了这个边界。

## 结果

| 指标 | 值 | 说明 |
|---|---|---|
| **正确文档进检索窗口**（旧 24 题集） | **2/24 → 21/24（8% → 87.5%）** | ★ 最硬的指标：**与阈值解耦**，纯排名质量 |
| 检索命中（L1，新 50 题集） | **45 / 50** | 来源 ∧ 探针（任一命中）；含 5 道库外拒答题 |
| 回答通过（L2，新 50 题集） | **50 / 50** | 含模型自身知识兜底——**5 道检索失败的题它照样答对** |
| 回归测试 | **110 用例** / 约 20 秒 | 默认**不调大模型**，只需本地 Ollama，**不需要 API Key**，可直接进 CI |

> ⚠️ **换过评测集，分数不可直接对比。** 旧的 `23/29` 和新的 `45/50` 不是同一把尺子：
> 旧 24 道库内题**全在 tutorial**，新 50 题按「基础 25 / 进阶 6 / API 签名 4 / 迁移配置 4 /
> 部署 4 / 概念 2 / 库外 5」分层。可比的是 tutorial 子集：**21/24 → 22/25**。
> `8% → 87.5%` 那一行仍是旧 24 题集的结果，用来说明 embedding 换代的量级，不要和新分混着讲。

### 分层水位（新 50 题）

| 层 | 题数 | 来源命中 | L1 |
|---|---|---|---|
| 基础用法（tutorial） | 25 | 22 | 22 |
| 进阶用法（advanced） | 6 | 6 | 6 |
| API 签名（reference） | 4 | 4 | 4 |
| 迁移与配置（how-to） | 4 | 4 | 4 |
| 部署运维（deployment） | 4 | 4 | 4 |
| 概念（async / 类型提示） | 2 | 1 | 1 |
| 库外拒答 | 5 | 4 | 4 |
| **合计** | **50** | **45** | **45** |

> 分层的意义：只报一个总数会掩盖"哪一层不行"。现在能看出**失败全部集中在 tutorial**（3/25）
> ——而 20 道新增题全过，原因是它们的问题里都带专有名词（WebSocket / Docker / GraphQL /
> HTTPS / UploadFile），跨语言检索天然占便宜。**纯中文概念**（查询参数、请求头、表单数据）
> 才是真正的难点，也恰好是失败的那三道。

**为什么指标要分两级**：`L2 = 50/50` 是**假象**——5 道题检索完全失败（甚至召回的是无关页），
模型靠自己会 FastAPI 照样答对。**只有 L1 能照出知识库的真实贡献。**
这个项目因此把两级指标分开统计，判断改动好坏只看 L1。

### 行为评测：一致性 / 鲁棒性

「单句正确率」测不出两类真实情况，所以单独建了 10 条用例：

| 类别 | 怎么测 | 结果 |
|---|---|---|
| **一致性** | 同一问题 3~4 种问法（"怎么配置跨域 CORS" / "跨域怎么设置" / "如何允许跨域请求"） | **11/14 命中（79%）** |
| **鲁棒性** | 加了噪声的问法：错别字、中英混输、多余全角标点、大小写 | **4/5 与基线一致**（第 6 条因基线本身失败而跳过） |

唯一断掉的是错别字：**"路径参树"**（数→树）——单字替换会把语义整段带偏，说明 bge-m3
对中文错别字不鲁棒。这条标了 `xfail` 留作活记录：哪天它开始通过，说明补了查询纠错或换了模型。

> 这两类参考了业界的行为评测分类（refusal / consistency / robustness / calibration / adversarial），
> 本项目原先只有 refusal（库外拒答），现在补上中间两类。

## 数据流

```
离线：docs_fastapi/*.md → 排除 changelog → 切块(500/50) → 块首补页面标题 → bge-m3 向量化 → Chroma
                                             └─ 库名带「文档指纹 + embedding 模型 + 块格式版本」

在线：问题 → ① 向量检索 k=5
            ② 阈值 0.32 过滤           ← 分数低于此的丢弃
            ③ ★ 联动闸门               ← 向量 0 条过阈值 → 直接返回空，禁用 BM25
            ④ BM25 补召最多 3 条        ← 仅在向量有命中时执行（可选：中文 query 先翻英文）
            ⑤ 去重合并，取前 6 块 → 拼上下文 → LLM 生成（带 [n] 引用）
```

## 七个关键决策

### 1. embedding 选型：8% → 75%

中文查英文文档，用英文主导的 `nomic-embed-text` 时**正确文档几乎进不了召回**。
**两个库并存做 A/B**（同语料、同 24 题，只换 embedding）：

| embedding | 正确文档进 top10 |
|---|---|
| `nomic-embed-text`（768 维，英文主导） | **2/24 = 8%** |
| **`bge-m3`（1024 维，多语言）** | **18/24 = 75%** |

> 这张表是当时的配置（k=4、未补块首标题），两侧同口径，A/B 才成立。
> 后来做了「关键决策 6」里的两步（补标题 + k=5），bge-m3 这一侧到 **21/24 = 87.5%**；
> nomic 那一侧没有重跑，所以别把它当成 8% vs 87.5% 的对比。

### 2. 阈值 0.32 不是拍脑袋

跑分数分布找"可分区间"：

| | top1 分数段 |
|---|---|
| 库内题（24 道） | **0.356 ~ 0.642** |
| 库外噪声（真无关） | **0.161 ~ 0.280** |

**中间 0.28 ~ 0.36 一条数据都没有** → 取这条空隙的中点 **0.32**。
放中间是因为**离两边都最远，容错空间最大**。

⚠️ **它不是常数**：换 embedding 后老阈值把召回全砍光（L1 掉到 5/29）。
已写成自动化测试 `test_threshold_sits_in_the_score_gap`——**忘了重标，测试立刻失败**。

### 3. 混合检索 + 联动闸门

两个检索器**盲区刚好互补**：

| | 向量 | BM25 |
|---|---|---|
| 强在 | **懂语义**——换种说法也能找到 | **认字面**——专有名词/代码符号一抓一个准 |
| 盲在 | ① 跨语言 ② 分不清同领域不同话题 | **完全不懂语义**——字面重合就给分 |

**实测一（它真的救回过一题）**：问「怎么读取 Cookie」时，正确页在向量里排 **第 57 名**
（0.438 分，k=5 根本够不着），BM25 给了 **8.68** 并直接命中 `cookie-params.md`。
这类"专有名词 / 代码符号"是 BM25 唯一稳定的贡献点 —— **它的净贡献就是这 1 题**（来源命中 20→21/24）。

**实测二（但它也只值 1 题）**：24 道库内题里 15 道 BM25 有命中，可**中位数只有 0.95** ——
8 道题拿到的是 0.95 的噪声块，白占 6 个名额里的 1 个。根因是中文问句打英文语料，词面本就不重叠。
去掉更新日志之后，BM25 那些 13~20 的高分也一起消失了（**那些高分本来就是 changelog 给的假象**）。
→ 下一步该做的是**查询先翻成英文再过 BM25**，而不是继续调 BM25 参数。

**代价**：BM25 没有"无关"这个概念，会带噪声 → 所以加了闸门。
**不是"多一个检索器"，是"多一个必须配一道门"。**

**闸门为什么必要**：向量是系统里**唯一能表达"这问题与知识库无关"**的组件。
实测：问「Python 的 GIL 是什么」时向量 0 条过阈值，**BM25 却从 `classes-as-dependencies.md`
给了 3.77 分**（就凭 "Python" 这个词撞上了）——没有闸门就会把这块塞进上下文。
→ **不能用"字面碰巧"否决"语义判断"**；且错误代价不对称（少召回无害，错召回有幻觉风险）→ 宁可空着。

> 另有三道完全无关的题（天气 / 美食 / 量子纠缠）BM25 本来就是 0 分 —— 闸门对它们是冗余的。
> 它真正起作用的是"有擦边字面重合"那一类，比如上面的 GIL。

### 4. 生成侧：实测后做的取舍

本机 **4GB 显存**，7B 装不下（会退化为 CPU 推理、单轮 30~60 秒）。
**实际测过本地方案**：`qwen3:4b` 体积刚好塞得进 4GB 显存，但**回答质量明显不足**。

**判断**：生成走云端 API，**embedding 留在本地** —— **知识库不出门**，只把"说话"这一步交给云端。
（这不是"硬件不行只能上云"，而是在约束下选的架构：**私有数据留本地，算力借云端的**。）

顺带发现：深度思考模型**默认开启推理**，同一问题烧 117 token（90 是内部推理），关掉只要 34 → **白烧 2/3**。

### 5. 先建度量再动手

任何改动之前先建评测集和两级指标。
反例：把阈值调低后**回答仍然全对**——表面"没变化"，实际是模型兜底盖住了检索失败。
**没有度量，你无法判断改动是好是坏。**

### 6. 三处改动各自的贡献（逐步归因，不是一次性调参）

| 改动 | 来源命中 | L1 |
|---|---|---|
| 基线（bge-m3，3929 块） | 18/24 | 21/29 |
| ① 排除更新日志（3929 → 1919 块） | 18/24 | 21/29 |
| ② 块首补页面标题 | 20/24 | 21/29 |
| ③ 向量 k 4→5（给 BM25 留 1 个名额） | **21/24** | **23/29** |

> 这张表是**旧 24 题集**上的逐步归因（四行同口径，所以有效）。
> 2026-10-22 重挑评测集后绝对值变了，但**结论方向没变**：补标题救「近失」、k=5 比 k=6 好。

① 是我一开始的猜测，**被数据否掉了**：changelog 占了库的 51%、BM25 上拿 13~20 分，
听起来完全像元凶，可删完 L1 一动不动 —— 它只是占了名额，没占住正确页该有的位置。

② 有效，但只对"近失"有效：#01 从第 11 名提到第 4 名、#03 从 5 提到 1；
排到 15~18 名的两道纹丝不动。**给块补标题能救"语义接近但没身份"的块，救不了语义本身不匹配的。**

③ 不是"越大越好"：k=6 时 BM25 一个名额都不剩，来源命中反而掉回 20/24。
**上下文的分配比总量更重要** —— 6 个位置里留 1 个给关键词路，比多要一个向量块值。

### 7. 查询翻译：诊断是对的，收益被「名额」吃掉了

**症状**：BM25 净贡献只有 1 题。原因很直白——中文 query 切成中文 token，英文语料里一个都匹配不上，
只有 Cookie / JWT / CORS 这类"跨语言同形"的词能撞上。

**做法**：中文问题先翻成英文关键词，**只喂给 BM25**（向量路仍用原句，因为 bge-m3 跨语言本来就强）。

**实测**（同一份 1919 块库、同一套 50 题）：

| 配置 | 来源命中 | L1 |
|---|---|---|
| 不翻译（k=5，默认） | 45/50 | 45/50 |
| 翻译 + 并集（k=5） | 47/50 | 47/50 |
| 翻译 + 并集（k=4） | **48/50** | **48/50** |

**翻译确实把 BM25 救活了**：三道失败题的正确页，BM25 分数从 0.53 涨到
11.75（查询参数）/ 13.89（请求头）/ 20.62（表单数据）。

**但端到端只 +2**：上下文只有 6 格，向量占 5 格，BM25 只有 1 格——**捞得再准也只进得去一条**。
这是这次最有价值的发现：瓶颈从"检索不到"变成了"名额不够"，两者要的解法完全不同。

两个反例比正例更值钱：

- **替换会丢分**：直接用译文替换原句，"怎么读取 Cookie" 反而查不到了（原句 BM25 8.30 命中
  `cookie-params`，翻成 "read cookies" 后 `response-cookies` 顶上来）。改成
  **原句与译文各检索一次、同一块取较高分**的并集，两头都保住
- **k=4 只在翻译开启时有意义**（48 vs 47）；不翻译时 k=4 掉到 43。**两个参数是耦合的**，
  不能单独调——这也是为什么默认配置没动 k

**默认关**（`QUERY_TRANSLATION=0`）：开一次翻译就多一次模型调用（+0.5~1.5s），
而且 110 条回归会从"本地离线、零成本"变成"要联网、会花钱、可能限流"。
有一条测试专门钉住这个默认值。

## 四个「不报错的」静默失败

**共同点：都不报错，只让结果悄悄变坏。** 程序照常运行、接口照常返回，只是答案越来越不对。

| # | 名字 | 症状 | 根因 | 现在的防线 |
|---|---|---|---|---|
| 1 | **幽灵文档** | 删掉的文件仍被检索到 | 建库只判断"库存在吗"，不判断"库还新吗" | 库名带语料指纹 |
| 2 | **空壳库** | 建库中途失败留下空库，之后永远跳过重建 | 就绪判断只看"目录非空" | 块数 > 0 才认（第二代） |
| 3 | **半截库** | 建到一半中断，库能答一部分问题、看起来"能用" | `count > 0` 仍然太松：`0 < count < 全量` 也算就绪 | **块数 == 预期块数**（第三代） |
| 4 | **换模型不换库** | 换 embedding 后静默用旧库 | 库名不含 embedding 模型名，拿旧维度向量配新维度查询 | 库名带模型名 + 阈值按模型查表 |

**判据演进本身就是最值得讲的一段**：`目录非空` → `count > 0` → `count == 预期块数`。
前两代都被真实事故打回过——第一代漏掉空壳库；第二代漏掉半截库，而半截库比空壳库更难发现，
因为它**能答一部分问题**。第三代把「预期块数」从「语料 + 切分参数」确定性推导出来
（加载和切分是纯文本操作，秒级、不调 embedding），顺带还解决了"改了切分参数不生效"这个问题。

**四个坑各有回归测试兜底**：`test_no_ghost_documents_in_index` /
`test_db_dir_encodes_embedding_model` / `test_db_ready_rejects_partial_library` /
`test_threshold_sits_in_the_score_gap`。

> **"我修过四个 bug" 不如 "这四个 bug 不会再发生"。**

## 快速开始

```bash
# 1. 依赖
pip install -r requirements.txt

# 2. 本地 embedding 服务（必须）
ollama pull bge-m3

# 3. 语料（FastAPI 官方文档，本仓库不含——别人的文档不该塞进自己的仓库）
git clone --depth 1 --filter=blob:none --sparse https://github.com/fastapi/fastapi.git fastapi-docs
cd fastapi-docs && git sparse-checkout set docs/en/docs && cd ..
cp -r fastapi-docs/docs/en/docs ./docs_fastapi
# 期望结果：154 个 .md（release-notes.md 会被 EXCLUDE_DOCS 跳过）

# 4. 密钥（**只跑回归测试可以跳过这一步**）
cp .env.example .env      # 填 ARK_API_KEY；ARK_MODEL 换成你控制台里开通的 Model ID

# 5. 首次运行会自动建库（1919 块，约几分钟）
python 14-ai_agent_assistant.py --test "FastAPI 怎么定义路径参数？"

# 交互模式
python 14-ai_agent_assistant.py
```

**看检索决策路径**（能打印出向量分数、阈值过滤、闸门判定、BM25 补召、最终上下文）：

```bash
python retrieval_trace.py "今天天气怎么样？" "FastAPI 怎么配置跨域 CORS？"
```

**跑回归测试**（不调大模型，约 15 秒，**不需要 API Key**）：

```bash
pytest                    # 默认只跑本地用例
pytest -m llm             # 附带需要调大模型的用例（要 ARK_API_KEY，会花额度）
```

**跑完整评测**（50 题，会调大模型、产生费用）：

```bash
python eval_fastapi.py
```

## 项目结构

```
14-ai_agent_assistant.py   主程序：建库 → 检索 → 生成（单文件，约 860 行，含大量决策注释）
eval_cases.py              评测集（50 题，分 7 层；含 L1 探针词 / L2 期望词 / 可接受来源）
eval_judge.py              判据（跑分脚本与测试套件共用，避免两处维护漂移）
eval_fastapi.py            跑分脚本（输出 L1 / L2 + 失败归因）
audit_probes.py            探针体检器：检查每个 L1 探针词是否「本页高频、全库低频」
retrieval_trace.py         可观测性：把检索决策路径结构化落盘 + 渲染
conftest.py / pytest.ini   测试夹具与配置
test_retrieval.py          回归测试套件（110 用例，含 5 条元测试 + 10 条行为评测）
requirements.txt           依赖（全部锁版本，实测通过）
.env.example               配置模板（真实 .env 不入库）
LICENSE                    MIT
```

**为什么评测集和判据要抽成独立模块**：跑分脚本和 pytest 套件必须用**同一份**定义，
否则会出现"测试过了但跑分不过"这类最难查的不一致。

## 已知局限

- **基础层还有 3 道「正确文档没进召回窗口」**——查询参数、请求头、表单数据。
  前两道要 k≥15 才够得着（上下文翻 2.5 倍），表单数据是向量和 BM25 都招不回，
  属数据层问题（中文「表单」和英文 Form Data 对不上），换窗口大小没用。
  **三道都集中在「纯中文概念」上**，而带专有名词的题（WebSocket / Docker / GraphQL）全过
  —— 这正是「中文问英文文档」的难点，也是查询翻译值得做的理由
- **查询翻译能救这 3 道，但默认关着**：开了以后 BM25 能命中正确页，整体 45 → 47；
  代价是每问多一次模型调用。不默认开的原因是回归套件要保持「离线、免费、无 key」
- **一个被我猜错过的地方**：我原以为 L1 卡住是因为 changelog 占了 51% 的库，
  结果是排除之后 L1 一点没变。写在这里是因为「以为→实测→推翻」比结论本身更有信息量
- **没上 rerank**——知道它治什么（同领域不同话题的噪声），但当前瓶颈在数据和排序，不在精排
- **评测集 50 题**——够看趋势，仍不足以对「2~3 题的改动」下结论（1 题 = 2pp）。
  要判断小改动得看机制证据（名次位移），不能只看计数
- **代码符号探针不可靠**——FastAPI 文档用 `{* ../../docs_src/xxx.py *}` 引代码，正文里符号稀疏
  （`BaseModel` 在目标页出现 0 次），已改用页内高频词
- **`index.md` 仍会偶尔进上下文**（`release-notes.md` 已在建库时排除）
- **换问法会丢 3/14、错别字会整条断掉**——前者是措辞敏感，后者是 bge-m3 对单字替换不鲁棒；
  两条都记在行为评测里，不是没发现，是明确知道边界在哪
